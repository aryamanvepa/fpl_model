FPL Multi-Model Bot

Four different ways to decide a Fantasy Premier League squad, run against each other, combined, and made fully inspectable.

I wanted to see what happens when you point several genuinely different decision-making approaches — a hand-tuned formula, a trained statistical model, an evolved strategy, and an LLM reading the news — at the same problem, and let them compete rather than picking one. This is that system: four models, each running its own live squad, combined by a weighted ensemble, with a dashboard that shows the actual internals (training curves, backtests, live weight sliders) rather than just a final recommendation.

The four models

ModelApproachMeasured result
1 — Evolutionary A genetic algorithm. A population of transfer/captaincy strategies plays simulated historical seasons; the best-scoring survive and breed the next generation — the same idea as the classic "AI learns to play the Chrome dinosaur game" videos, applied to squad selection instead. Beat a sensible non-evolved baseline by +101 points over a full held-out season it never trained on, while taking a third as many transfer hits.
2 — Statistical Gradient-boosted trees, trained on 3 seasons of real gameweek data, predicting expected points from features knowable before kickoff only (recent form, fixture difficulty, home/away, price). MAE 1.02 vs. 1.08 for a naive rolling-average baseline on a held-out season — a real, modest, honestly-reported edge.
3 — Basic stats A transparent, hand-weighted formula (points-per-game, value, ICT index, expected goal involvement, expected goals conceded), weighted differently per position. No ML — the fast-to-ship baseline the other models get measured against.
4 — Qualitative An LLM (local Ollama or the Anthropic API) reads recent football headlines and official injury/status notes for a shortlist of players, and reasons about score adjustments with a rationale attached. Single-pass synthesis rather than a multi-turn tool-using agent — deliberately simple for a fixed daily source list.

Every model's output — whatever form it takes internally — becomes a per-player score fed into a shared integer linear program (via PuLP) that picks the actual best legal 15-man squad: real budget, real 3-per-club cap, real formation rules. So every model produces a genuinely valid squad, not just a ranking.

Combining them

The four models score players in incompatible units — Model 2 outputs predicted points (roughly 0–8), Model 1 a genome-weighted linear score (roughly −3 to 3), Models 3 and 4 a 0–1 composite. Averaging those directly would just let whichever model happens to use the widest numeric range dominate for no principled reason.

Instead, each model's scores are converted to a percentile rank within that model first (0 = that model's worst pick, 1 = its best), and only the ranks get combined — weighted by what's actually been backtested. Models 1 and 2 (both measurably beat a naive baseline) get the most weight; Model 3 (unvalidated hand-tuned formula) less; Model 4 (no live backtest yet) least. If a model's backend is unavailable on a given run (e.g. Ollama not running), it drops out and the remaining weights redistribute automatically rather than the whole run failing.

Five live teams, one ruleset

Each model runs its own team, plus a fifth managed by the ensemble — five independent, simultaneously-tracked squads so the models can be compared on live results, not just backtests. All five follow the same mixed-autonomy rule: captain and bench-order changes auto-apply (low-risk, easily corrected next week), while anything that changes squad composition — the first-ever draft, or a transfer — queues for manual approval instead of executing automatically.

Running weekly, on its own

A scheduled task checks daily whether the next gameweek deadline is within 60 hours, rather than firing on a blind fixed weekly day — deadlines shift (postponements, double/blank gameweeks, international breaks moving a deadline to Monday), so the check reads the real deadline out of the data instead of assuming one. Once triggered, it refreshes data, runs all four models plus the ensemble, diffs against each team's held squad, and queues transfers — once per gameweek, tracked so a deadline that's "close" on both Thursday and Friday doesn't trigger the run twice.

Making it inspectable

The part I cared about most: a dashboard that shows how each model actually thinks, not just what it outputs.

  • Model 3's weights are live sliders — drag one and every ranking and chart recomputes immediately.
  • Model 1 has a slider across generations — scrub through training and see exactly what the evolved strategy valued at that point, and what squad that generation's version of it would draft for the current live gameweek.
  • Model 2 shows a predicted-vs-actual scatter on real held-out data, plus on-demand permutation feature importance (shuffle a feature, measure how much worse predictions get).
  • The ensemble page shows, for any player, exactly which of the four models ranked them well and by how much — not just the final blended number.
  • Every model page ends with that model's actual current squad, computed live from whatever's on screen.

What's still rough

Built to be honest about its own limitations, not just its results:

  • Model 1's season simulator: at most one transfer evaluated per week, no bench autosubs, no chips (wildcard, free hit, bench boost, triple captain) yet.
  • Model 4 has never had a live LLM backtest in the environment it was built in — the pipeline is fully tested with a stubbed response, but real-world accuracy is unmeasured.
  • No real FPL account integration yet — the five teams' state is tracked locally, not against actual FPL accounts.

Stack

Python throughout. PuLP for the ILP squad optimizer, scikit-learn for the gradient-boosted predictor, a from-scratch genetic algorithm for the evolutionary model, Streamlit + Plotly for the dashboard, SQLite for storage. Data from the official FPL API and the public vaastav/Fantasy-Premier-League historical dataset.
